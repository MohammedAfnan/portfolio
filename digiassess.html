Work / Design system for an assessment platform

Exam day ran on 8 blues. One of them passed contrast.

I rebuilt DigiAssess on one token set. Students, proctors, exam co-ordinators and schedulers now share 35 semantic colours, two themes and one type ramp. Every colour pair is checked against WCAG AA in both themes.

Problem

A proctor watches 35 students on one screen. The colours could not tell him who needed help first.

I audited 10 screens: scheduling, assessment creation, outcome analysis, the co-ordinator dashboard, proctor monitoring and the student exam. Four problems came up on every one of them.

Eight blues, no rules

Links, buttons, headers and selected states each used a different blue. Nobody could say which one was the brand.

Status by colour alone

Red text meant support requested. Green meant on time. For a proctor with red-green colour blindness the two look alike.

Small grey text

Captions in #979797 measured 2.9:1 on white. AA asks for 4.5:1. The green nav label on the blue header measured 2.4:1.

One bright theme

Proctors and co-ordinators watch the same screen for a full session. There was no dark theme and no tokens to build one with.

Four users, one system:Student reads and answersProctor sees exceptions firstCo-ordinator sees the whole sessionScheduler sees dates and clashes

Rules I set for the system

Five rules every token and component had to pass.

Named for the jobbrand/default, not blue/600. Screens never touch a raw hex value.
AA or it does not ship4.5:1 for text. 3:1 for borders, icons and chart marks. Checked in both themes.
Never colour aloneEvery status has a shape and a word. The screen still works in greyscale.
Dark is a modeA theme switch changes the alias, never the component.
Reading gets its own typeQuestion stems use Atkinson Hyperlegible, drawn by the Braille Institute for low-vision readers.

Foundation one: tokens

Three colour layers. Screens only ever see the top two.

Primitives hold raw values and are hidden from the library, so nobody picks blue/600 by mistake. Semantic tokens say what a colour is for and carry the Light and Dark modes. Component tokens point at semantic ones, so a button can change without touching the theme.

Foundation three: space, shape and depth

A 4px grid, six radii and three shadows. Density is a mode.

The old screens had 33 corner radii, from 2 to 103. The new set has six. Density lives in its own collection, so the proctor table can run Compact while the student exam stays Comfortable, with the same components.

The exam co-ordinator had ring charts, a feed sorted by time and a red pill for Live. The rebuild answers one question first: who needs me right now?

Screen theme

Switch the screen theme above. Only one attribute changes on the screen.

One switchThe dark screen sets data-theme on one element. No component is restyled.
Brand moves to blue/400On-brand text flips to near black so the button keeps 5.7:1.
Depth by shadeCanvas 950, cards 900, table header 850. The layers read without shadows.

Charts swap togetherAll five data colours move to their 400 step and still pass 3:1.

What I’d do differently

Start from the student exam screen, not the dashboard.

Start where reading is hardest

I built the tokens from the co-ordinator screens first. The student exam has the strictest needs: long stems, a timer and zoom to 200%. Starting there would have settled the type ramp sooner.

Test dark mode in the room

The contrast checks are maths. Glare and fatigue in an exam hall are not. I’d run one live session with proctors before calling the theme done.

Add a high-contrast mode

The colour collection is ready for a third mode. Students who need stronger contrast should get it without a single new component.

Write the Android rules next

The exam app shares the tokens but not the touch targets. Answer rows and question cells need their own density values there.
