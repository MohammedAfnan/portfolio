Work / Hiring funnel for a recruiter app

Recruiters had every count. They couldn’t see where candidates stopped.

I redesigned the vacancy table in Sieve, a mobile app for recruiters. Ten columns became a funnel you read top to bottom, and every count opens the people behind it, already filtered.

Problem

A recruiter runs a dozen vacancies from a phone. The vacancy table is four phones wide.

The table had one row per vacancy and one column per hiring step, from Define vacancy to Close hiring. It held the right numbers. On a 360 px screen it showed the vacancy name and one column.

Wider than the screen

Ten columns. In the original file the table is 3.8 times the width of the phone beside it. Everything past the second column is a sideways swipe.

Counts without the drop

256, 138, 56, 46, 36, 10, 4, 2. Where people stop is a sum the recruiter does in their head, per vacancy, every morning.

Header and cell disagree

Headers name the next task. Cells name the current result. “Shortlist recommended” sits over “46 Recommended”, so 46 reads as shortlisted.

A number is a dead end

No count is marked as tappable. Seeing the 56 eligible people means leaving the table and building a search by hand.

Rules I set for the numbers

Five rules every count on screen had to pass.

Every count opensTap a number, get the people behind it, already filtered.
Show the dropA rate between every pair of stages. The worst one gets a flag.
One name per stageStages are results. Tasks become buttons on the stage.
Count before ApplyEach filter option says how many it leaves. So does the button.
No dead endsAn option that would leave nobody shows its zero and greys out.

Screen one: vacancies

Twelve vacancies, sorted by what needs the recruiter.

Each card carries a small funnel and one line that says where the vacancy is stuck. The chips on top filter the list and show their counts before anyone taps.

Screen two: the funnel

The table, turned on its side.

Columns became rows, so a phone shows all eight stages without a swipe. Bars give the shape. The rate between rows shows where people stop, and the lowest rate gets the flag.

Screen three: filtering

Filters that say how many people they leave.

Tapping Eligible opens the 56 people in that stage. Stage tabs keep their counts, applied filters stay on screen as chips, and the sheet shows a count next to every option.

The filter sheet, live

Tap the options. Counts and the button update from 56 mock candidates.

Decision

Three ways to fit a ten-column table on a phone.

The original file had two directions: the wide table and a card with a progress bar. I added a third and checked each against one question. How many people are stuck, and where?

Wide table, first column frozen

Best for
Tablets and web, where all ten columns fit.
Trade-off
On a phone it is still four screens wide. Rates need an extra row.

Progress card, from the file

Best for
A quick look at whether a vacancy is moving.
Trade-off
The bar hides every count. “Status: Ongoing” does not say what to do.

Vertical funnel

Best for
Phones. Eight stages top to bottom, with a rate between each.
Trade-off
One vacancy per screen, so the list needs a smaller version.

Funnel on the detail screen, an eight-bar sparkline on the list card, and the table kept for tablet and web. All three use the same stage names and the same counts.

How I counted

Phone widths: in the file’s reference frame the table is 1,094 px wide beside a 285 px phone, 3.8 widths. The funnel fits all eight stages on a 360 by 780 screen.

Rates: the table showed eight counts and no rates. The funnel shows one for each of the seven steps between stages.

Names: every column had a task header and a result cell. Each stage now has one result name, and the task is its button.

Taps: no count in the table had a tap target. In the funnel all eight counts open a filtered list in one tap.

These are counted from the screens, not measured with users. Usage numbers would come after launch.

What I’d do differently

Four things I’d change next time.

Start from real vacancy data

Some roles skip stages, like campus hires with no screening. I’d count how many before fixing the funnel at eight rows.

Confirm stage dates exist

Time in stage needs the date each person entered it. The old table only had “5 m”. I’d ask engineering in week one.

Plan for very large funnels

A role with 2,000 sourced squashes the lower bars to slivers. I’d test a capped scale before the layout was final.

Ship saved filters on day one

A recruiter who wants score 70+ and notice under 30 days sets both again on every vacancy. I’d let them save the pair once.
